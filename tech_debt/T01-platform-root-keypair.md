# T01 — Корень доверия: убрать закоммиченный приватный ключ платформы

- **Приоритет:** 10/10
- **Стадия:** Stage 1
- **Область:** backend · packages/verifier
- **Статус:** backlog

## Что не так

Приватный ключ платформы (`PLATFORM_PRIVKEY`, PKCS#8 Ed25519, префикс `e08496…`) закоммичен в двух местах:

- `packages/verifier/src/verify.test.ts:5`
- `backend/src/crypto/__fixtures__.ts:10`

Этот приватный ключ **является** парой к pinned-публичному ключу `DUO_MESH_PLATFORM_PUBKEY` (`packages/verifier/src/verify.ts:133`, значение `3ac4ff…`). То есть закоммичен именно приватный ключ корня доверия всей провенанс-системы.

## Почему это важно

Два взаимоисключающих сценария, оба сломаны:

1. **Прод использует эту пару.** Тогда приватный ключ публичен (любой, у кого есть доступ к репозиторию, может подписать произвольную провенанс как `PLATFORM`). Офлайн-верификатор примет поддельную цепочку за `valid` — полный компрометация модели доверия, ради которой и существует офлайн-верификация.
2. **Прод сгенерировал случайный ключ** (`SigningService.ensureKeys()`, `backend/src/services/signing.service.ts:77-94`, генерирует платформенный ключ при отсутствии). Тогда pinned-ключ не совпадает с продом, и **каждый** реальный экспорт проваливает проверку «платформенной косинь против pinned-ключа» — офлайн-верификация сообщает `invalid` на настоящих сертификатах.

Тесты проходят только потому, что подписывают закоммиченным приватным ключом.

## Локализация

- `packages/verifier/src/verify.ts:133` — pinned `DUO_MESH_PLATFORM_PUBKEY`.
- `packages/verifier/src/verify.test.ts:5` — приватный ключ.
- `backend/src/crypto/__fixtures__.ts:9-10` — публичный + приватный ключ.
- `backend/src/services/signing.service.ts:77-94` — `ensureKeys()` генерирует ключ при отсутствии.
- `backend/src/crypto/tamper.test.ts` — потребитель `mintSignedExport`.

## Минимальная правка

1. **Определить, какой ключ в проде.** Прочитать `signing_keys` (строка `owner_type = 'PLATFORM'`, активная) и сравнить публичную часть с `DUO_MESH_PLATFORM_PUBKEY`. Это первый шаг и требует доступа к продовой БД.
2. **Убрать приватный ключ** из `__fixtures__.ts` и `verify.test.ts`.
3. **Сделать trust-anchor инжектируемым** в верификаторе: `verifySignedExport(data, opts?: { platformPubKey?: string })` с дефолтом на константу — чтобы тесты могли генерировать ephemeral ключ и проверять логику без закоммиченного секрета.
4. **В бэкенд-фикстуре** `mintSignedExport` принимать ephemeral платформенную пару (генерировать в тесте) и пробрасывать её публичный ключ в верификатор через опцию.
5. **Добавить startup-проверку** в `SigningService`: при холодном старте логировать жёсткое предупреждение, если активный платформенный публичный ключ ≠ pinned.

## Подводные камни

- **Ротация прод-ключа — это не мелкая правка.** Если прод реально использует закоммиченную пару, её ротация требует перевыпуска всех экспортов/подписей. НЕ ротировать в этой задаче — только определить факт и задокументировать, ротацию вынести отдельно.
- **Нельзя просто удалить приватный ключ из теста:** бэкенд-фикстура подписывает им, а верификатор сверяет с константой. Без инжектируемого trust-anchor тесты перестанут проходить. Отсюда шаг 3 — инъекция опции.
- **Публичный ключ можно коммитить** (это и есть смысл trust-anchor), секрет — только приватный. Не путать.
- **`platform.publicKey` в экспорте информационный** (`verify.ts` комментарий) — верификатор использует только константу. Не «чинить» это в рамках задачи.

## Приёмочные критерии

1. `PLATFORM_PRIVKEY` больше не встречается ни в одном файле под `git grep`.
2. `bun test` в `packages/verifier` и `backend` зелёные (тесты подписывают ephemeral ключом).
3. Задокументировано, какой ключ реально в проде (совпадает/не совпадает с pinned).
4. Startup-проверка логирует предупреждение при расхождении ключей.

## Валидация
