# T07 — `handleError` отдаёт клиенту стектрейс

- **Приоритет:** 8/10
- **Стадия:** Stage 1
- **Область:** backend
- **Статус:** backlog

## Что не так

`backend/src/http/errors.ts` L57-60: общая ветка `handleError` возвращает `errorResponse('INTERNAL_ERROR', message, stack)` — полный `error.stack` сериализуется в тело 500-ответа.

## Почему это важно

Любая необработанная ошибка (Prisma-ошибка, провал расшифровки keystore из KDF-бага и т.п.) раскрывает клиенту внутренние пути файлов, внутренности драйвера БД, возможно id ключей — утечка информации на каждом 500. Совмещается с T04/T05: на проде 500 при подписи как раз роняет стек.

## Локализация

- `backend/src/http/errors.ts:57-60` — `errorResponse(..., stack)`.

## Минимальная правка

Логировать `stack` на сервере (`console.error`), в теле возвращать только generic `message` (без `stack`).

## Подводные камни

- **Не потерять диагностику** — стек должен остаться в логах (Vercel runtime logs), только не в ответе.
- **Проверить всех вызывающих** `handleError`/`errorResponse` — убедиться, что никто не полагается на `stack` в теле (например, тесты).
- **`INTERNAL_ERROR` message тоже не должен содержать чувствительного** — если message приходит от Prisma-ошибки с SQL-деталью, рассмотреть обобщение в проде.

## Приёмочные критерии

1. 500-ответ не содержит `stack` (ни в JSON-теле).
2. Стек присутствует в серверном логе.
3. `bun run --cwd backend test:unit` зелёные.

## Валидация

```bash
bun run --cwd backend test:unit
# локально: вызвать роут, дающий 500, и убедиться, что body без stack
```
